# 04. 音声

接続先での仮想マイクと録音要求の検出、接続元でのマイク取得、そのあいだのバッファと実測値をまとめる。

---

## 1. 仮想マイク

### 1.1 null sink と monitor source

PulseAudio の null sink を 1 つ作る。その monitor source が、アプリから見える録音デバイス（仮想マイク）になる。

```
client からの PCM → pacat → null sink "micmux" → monitor source "micmux.monitor" → アプリ
```

- sink の形式は 16 kHz / モノラル / s16le。名前は既定で `micmux`（`--sink-name` で変えられる。
  英数字と `_` `-` だけ）。
- 既に同じ名前の sink があれば、作らずにそれを使う。**自分で読み込んだ module だけを、終了時に unload する。**

### 1.2 `pactl` / `pacat` を子プロセスとして使う（決定）

bridge は libpulse にリンクせず、`pactl` と `pacat` を子プロセスとして起動する。

- 接続先のビルドに、開発ヘッダが要らない。
- PulseAudio 互換の範囲しか使わないので、pipewire-pulse でも動く見込みがある（未確認）。
- `pactl` の出力は、ロケールで表記が変わらないよう `LC_ALL=C` で読む。

### 1.3 アプリに仮想マイクを使わせる

- `--set-default`: 接続中だけ、仮想マイクを接続先の**既定の録音デバイス**にする。終了時に元へ戻す。
- 既定を変えたくない場合は、使いたいアプリにだけ環境変数で指定する: `PULSE_SOURCE=micmux.monitor`。
- 既定のデバイスを**無条件には変えない**（決定）。`--set-default` は明示したときだけ効く。

## 2. 録音要求の検出

### 2.1 状態は、イベントからではなく現在の集合から導く（決定）

`pactl subscribe` で、録音ストリーム（source-output）の増減と変化を監視する。ただし、イベントを
そのまま START / STOP に変換しない。イベントが来るたびに `pactl list source-outputs` を取り直し、
**「仮想マイクに繋がっていて、cork されていない録音ストリームの数」**を数えて状態を決める。

- 数が 0 → 1 以上: START を送る。
- 数が 1 以上 → 0: **300 ms 待ってから** STOP を送る。待っているあいだに再び 1 以上になれば、取り消す。
- 起動時にも 1 回数える（既に録音中のアプリがあるかもしれない）。
- イベントを取りこぼした場合の保険として、30 秒ごとに数え直す。

### 2.2 STOP を 300 ms 遅らせる理由

Claude Code は、本番の録音の直前に、ごく短い試し開きを 1 回する。これを別々のセッションにすると、
接続元のマイクが開いて閉じてまた開くことになる。猶予を置いて 1 セッションにまとめる。

## 3. アプリ側の録音経路（Claude Code）

仮想マイクが使われるかどうかは、アプリがどうやって録音するかで決まる。Claude Code 2.1.332 について、
バイナリの解析と実測で確かめたこと:

- Linux では、次の順で録音方法を選ぶ。
  1. 内蔵の録音モジュール（cpal。ALSA を直接使う）。`/proc/asound/cards` にカードがあるとき。
  2. `arecord`
  3. SoX の `rec`
- **PulseAudio を直接は使わない。** ALSA の既定デバイスを開く。そのため、ALSA から PulseAudio へ繋ぐ
  プラグイン（Debian では `libasound2-plugins`）が要る。Debian の `pulseaudio` パッケージは、サーバーが
  動いていれば ALSA の既定をそちらへ向ける設定を入れる。
- **録音ストリームは、キーを押すと作られ、離すと破棄される。** 常時開きっぱなしにはしない。
  これが成り立つので、§2 の検出が成立する。
- 要求する形式は 48 kHz / float32 / モノラル。sink との違いは、音声サーバーが変換する。
- SSH 越しであること自体は、音声機能を無効にする条件になっていない。
- サウンドカードが 1 枚も無く `arecord` も無い接続先では、録音方法を見つけられない。`alsa-utils` を入れる。

Codex CLI 0.162.1 の Linux 版（musl の静的リンク）には、ALSA や PulseAudio を呼ぶ痕跡が無かった。
Linux 版では録音できない可能性が高いが、**実際に起動しては確かめていない**。

## 4. 接続元でのマイク取得

取得の方法は 2 つある。

| 方法 | 指定 | 中身 |
|---|---|---|
| 内蔵 | 既定 | cpal で既定の入力デバイスを開く。macOS では Core Audio |
| 外部コマンド | `--capture-cmd <cmd>` | `sh -c` で実行したコマンドの標準出力を、s16le のモノラルとして読む |

- **録音セッションごとに取得用のスレッドを立て、止めるときはスレッドごと終わらせる。**
  待機中はデバイスを開かない。
- 内蔵の取得は、デバイスの既定の形式で開き、モノラルに混ぜて s16 にする。
- 外部コマンドは、内蔵の取得が動かない環境の逃げ道であり、試験にも使う
  （例: `rec -q -t raw -r 16000 -e signed -b 16 -c 1 -`）。出力のレートは `--capture-rate` で伝える。
- 外部コマンドを止めるときは、kill してから待つ。標準出力だけ閉じて動き続けるコマンドでも、
  待ち続けないようにする。

### 4.1 リサンプリング

- **16 kHz の整数倍のレート**（48 kHz・96 kHz）は、接続元で 16 kHz に落としてから送る。
  単純な間引きは折り返し雑音を生むので、Blackman 窓の sinc ローパス（遮断は出力のナイキスト周波数の 0.9 倍）を
  通してから間引く。
- **それ以外のレート**（44.1 kHz など）は変換せずに送り、接続先の音声サーバーに任せる。
- 専用のリサンプリングのライブラリは使わない（決定）。整数比の間引きだけなら数十行で済む。

### 4.2 圧縮しない（決定）

16 kHz / 16 bit / モノラルは 32 KB/秒（256 kbit/秒）。SSH と TCP のヘッダーを含めた実測で、
約 300〜360 kbit/秒である。録音中にしか流れないので、Opus などのコーデックは入れない。

無音のあいだ送らない仕組みも入れない（決定）。節約できるのは「キーを押したまま黙っている時間」だけで、
語頭・語尾が欠けて認識精度が落ちるおそれのほうが大きい。

## 5. バッファ

- **ジッターの吸収は `pacat` のバッファに任せる**（決定）。自前のジッターバッファは持たない。
  バッファ長は 60 ms（`--latency-ms`）。音声が届かないあいだ、null sink は無音を流す。
- **`pacat` は録音セッションごとに起動し直す。** 止めるときは残りを捨てて即座に止める
  （録音側はもう閉じているので、流し切っても誰も聞いていない）。
- **クロックドリフトの補正はしない**（決定）。セッションごとにバッファを作り直すので、ずれが溜まらない。
  27 秒の連続録音でも遅れは溜まらなかった（§6）。数十分の連続録音での挙動は未確認。

gap: bridge のメインループは、`pacat` への書き込みを同期的に行う。音声が実時間より速く届くと、
書き込みで止まり、録音の終了を検出できなくなる疑いがある（要調査。
[#6](https://github.com/Daiius/micmux/issues/6)）。

## 6. 実測値

接続元 macOS（Apple シリコン・内蔵マイク）、接続先 Debian、往復 約 10 ms の回線で測った（2026-11-27）。

| 区間 | 値 |
|---|---|
| 録音要求を受けてから、マイクが最初の音声を出すまで（接続元で計測） | 105〜110 ms。起動直後の初回だけ 約 140 ms |
| 同じ区間を接続先から見た値（通信の往復を含む） | 110〜118 ms |
| 接続先のバッファ | 60 ms（設定値） |
| 通信の往復 | 6〜12 ms |
| 転送量 | 約 32 KB/秒（録音中のみ） |

- 端末用の接続と分けた場合と、`--mux` で相乗りした場合とで、差は無かった。
- 27 秒の連続録音で、受信した音声の長さは録音時間と 0.1 秒差だった。遅れは溜まらない。
- 連続録音の上限を外して 3 分以上続けても、転送は続いた。
- **文字起こしにかかる時間は、micmux の外であり、ここに含まれない。** 体感の遅れがあるとすれば、
  大半はそちらである。

**接続元が Linux の場合**（ALSA → PulseAudio 経由で取得）、マイクの起動に 0.6〜1.0 秒かかった。
発話の冒頭が欠けやすいので、キーを押してひと呼吸おいてから話す必要がある。

### 6.1 発話の冒頭の欠落

録音要求が来てからマイクを開くので、開くまでの音は届かない。これは、オンデマンドで起動する方式に
固有の性質である。macOS では約 110 ms で、アプリ側のキー長押しの判定時間に隠れる程度だった。

常時録音しておいて直前の音を足す方式（プリロール）は、**採らない**（決定）。待機中にマイクを開かない、
という性質を捨てることになるため。armed のあいだだけ開きっぱなしにするモードは、遅延が問題になった
場合の選択肢として残す（[07](./07-roadmap.md)）。
