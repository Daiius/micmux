# 01. 動機と要求

なぜ「接続元で文字起こししてテキストを送る」のではなく、**音声そのものを接続先へ転送する**のか。
この章は、その判断と、そこから出てくる要求をまとめる。

---

## 1. 動機

### 1.1 想定する使い方

- 接続元: macOS のノート PC。
- 接続先: ヘッドレスの Debian の開発サーバー。
- 接続: SSH（直接接続、またはトンネル経由）。その上で tmux を使う。
- 接続先で動かすもの: コーディングエージェントの CLI（Claude Code など）。

コーディングエージェントは音声入力を備えているが、SSH 先で動かしていると、手元のマイクは使えない。

### 1.2 なぜエージェント標準の音声入力を使うのか

- **音声認識エンジンを自分で選定・運用したくない。**
- **日本語と英語の技術用語が混ざる入力**を、エージェント側の認識にそのまま任せたい。
- **既存の SSH + tmux の環境を変えたくない。** 特定のターミナルエミュレーターにも依存したくない。

### 1.3 汎用ツールとして作る

マイクの転送は tmux にもコーディングエージェントにも依存しない機能なので、独立したツールにする。
エージェントの協調ツール（bellmux など）からは**任意の連携先**として扱い、micmux の側からは依存しない。

ただし、現時点で実際に動作を確認した利用者（接続先のアプリ）は **Claude Code だけ**である
（[04](./04-audio.md) §3 / [07](./07-roadmap.md)）。「エージェント非依存」は設計上の性質であって、
複数のアプリで確かめた事実ではない。

## 2. 要求

### 2.1 機能

- 接続元の物理マイクを使う。接続先に仮想マイクを提供する。
- 接続先のアプリは、仮想マイクを**通常の録音デバイス**として使える。
- 接続先で録音要求が発生したことを検出し、それに応じて接続元のマイクを起動する。要求が終われば止める。
- 録音要求が無いあいだは、マイクを開かず、音声を送らない。
- 音声は SSH 経由で送る。
- **録音の最終的な許可・拒否は接続元が決める。**

### 2.2 非機能

- 待機時の CPU 使用率と消費電力が低い。
- 録音開始の遅延が小さい（[04](./04-audio.md) §6 の実測値）。
- 接続が切れたとき、接続元のマイクは確実に止まり、接続先は元の状態に戻る。
- 外部への依存が少ない。CLI で運用できる。
- 既存の SSH 設定（`~/.ssh/config`・Host の別名・鍵・エージェント・踏み台）をそのまま使える。
  SSH の認証情報を独自に保存しない。

### 2.3 対応する環境

| 側 | 対応 | 状況 |
|---|---|---|
| 接続元 | macOS | 実機で確認済み |
| 接続元 | Linux | 動く（`native` feature か `--capture-cmd`）。マイクの起動が遅い（[04](./04-audio.md) §6） |
| 接続元 | Windows | **未対応**。Unix ソケット・シグナル・`sh -c` に依存しており、ビルドも通らない |
| 接続先 | Linux + PulseAudio | Debian 13 / PulseAudio 17.0 で確認済み |
| 接続先 | Linux + pipewire-pulse | CI の通しの試験で確認（[04-audio](./04-audio.md) §1）。実際の音声デバイスがある機械では**未確認** |

## 3. 検討した代替手段

### 3.1 接続元で文字起こしして、テキストを送る

- 利点: 仮想マイクも音声の転送も要らない。通信の品質に左右されにくい。
- 採らなかった理由: §1.2 のとおり、エージェント標準の音声認識を使えなくなる。

### 3.2 接続元のキーバインドでマイクを起動し、同時に接続先を操作する

- 採らなかった理由: 接続元と接続先の状態の同期、長押しの再現、ターミナルエミュレーターへの依存、
  エージェントごとのキー割り当ての違い、tmux のペインの識別、macOS の入力監視の権限、と課題が多い。
- 接続元のキーバインドは、**録音許可の切り替え**（`micmux toggle`）に使う位置づけにする（[05](./05-security.md) §2）。

### 3.3 リバースポートフォワーディングで接続先から接続元へつなぐ

- 採らなかった理由: 接続先の `localhost` にポートが開く。ポートにはユーザーごとの権限が無いので、
  同じサーバーの他の利用者が録音要求を出せてしまう（[05](./05-security.md) §3.1）。

### 3.4 エージェントの公式のリモート開発機能・既存の OSS

- **未調査のまま実装に進んだ。** 当初の計画では、公式の GUI のリモート接続機能や、既存のマイク転送の OSS
  （claude-ssh-voice・mictunnel・micbridge・Roc Toolkit・PulseAudio のネットワーク機能）を先に調べることに
  していたが、接続先での実現可能性の検証を優先した（[decisions](./_grilling/decisions.md)）。
- 帰結: 新規開発が本当に必要だったかは、検証していない。同等の機能を持つものが見つかった場合に、
  乗り換えや取り込みを検討する余地は残っている。
- 一点だけ、実装の中で確かめたことがある。Claude Code は接続先にサウンドカードがあると内蔵の録音経路を
  優先するため、**`arecord` を差し替える方式は、サウンドカードのある接続先では効かない**（[04](./04-audio.md) §3）。
