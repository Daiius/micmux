## 決定ログ

### 既存機能と OSS の調査を飛ばし、接続先での実現可能性を先に確かめる（2026-11-27）

- **経緯**: 設計メモは、最初に「公式のリモート開発機能や既存の OSS で目的を達成できないか」を調べることに
  していた。一方で、最大の不確実性は「接続先のアプリが、録音の開始・終了に合わせて録音ストリームを
  作り、破棄するか」だった。これが成り立たなければ、設計そのものが成立しない。
- **決定**: 調査より先に、接続先の実機で確かめる。結果、Claude Code は録音ストリームをキー操作ごとに
  作って破棄することがわかり、そのまま実装に進んだ。
- **帰結**: 新規開発が本当に必要だったかは、検証していない（[01](../01-motivation.md) §3.4）。

### 録音要求は、接続先の音声サーバーの録音ストリームから検出する（2026-11-27）

- **決定**: 仮想マイクに繋がっていて cork されていない録音ストリームの数を数え、0 と 1 以上の境目で
  START / STOP を出す。イベントをそのまま変換せず、イベントのたびに数え直す。
- **根拠（実測）**: Claude Code 2.1.332 を tmux の中で起動し、キーの長押しを模擬した。録音ストリームは
  押すと作られ、離すと破棄された。TTS で作った音声を仮想マイクに流すと、正しく文字起こしされた。
- **STOP の猶予 300 ms**: 本番の録音の直前に、短い試し開きが 1 回あることを観測した。別々のセッションに
  しないための猶予である（[04](../04-audio.md) §2.2）。

### アプリは PulseAudio を直接使わないので、ALSA のプラグインを必須にする（2026-11-27）

- **経緯**: 設計メモは、アプリが PulseAudio の API で録音する場合を理想としていた。
- **わかったこと**: Claude Code は cpal で ALSA の既定デバイスを開く（バイナリの解析で確認）。
  接続先にサウンドカードがあると、`arecord` より内蔵の経路を優先する。
- **決定**: 仮想マイクは PulseAudio に置いたまま、ALSA から PulseAudio へ繋ぐプラグインを必須にする。
  `arecord` を差し替える方式は採らない（サウンドカードのある接続先では効かない）。

### bridge は libpulse にリンクせず、`pactl` / `pacat` を子プロセスとして使う（2026-11-27）

- **経緯**: 設計メモは `libpulse-binding` を候補にしていた。
- **決定**: 子プロセスにする。接続先のビルドに開発ヘッダが要らず、pipewire-pulse との互換も保ちやすい。
  実装時、接続先には開発ヘッダが無く、sudo も使えなかったことが直接のきっかけだった。
- **代償**: 録音ストリームの一覧を、`pactl` の表示から読み取る（`LC_ALL=C` で固定）。

### 依存 crate を `libc` と `cpal` だけにする（2026-11-27）

- **経緯**: 設計メモは、clap・serde/toml・tokio・tracing・rubato・libpulse-binding を候補にしていた。
- **決定**: どれも入れない。引数は手で解釈し、並行処理はスレッドとチャネルで書き、リサンプリングは
  整数比の間引きだけを自前で持つ。設定ファイルは持たない。
- **理由**: 実装してみると、テスト込みで約 2,700 行に収まった。設計メモは、問題の大きさに対して重かった。

### ジッターバッファ・ACK・クロックドリフトの補正を持たない（2026-11-27）

- **決定**: バッファリングは `pacat` に任せる。`pacat` を録音セッションごとに起動し直すので、前のセッションの
  残りが混ざらず、ずれも溜まらない。START に対する確認応答は置かない。
- **根拠（実測）**: 27 秒の連続録音で、受信した音声の長さは録音時間と 0.1 秒差だった。
- **残る課題**: `pacat` への書き込みが同期的であること（[#6](https://github.com/Daiius/micmux/issues/6)）。

### マイクの取得は外部コマンドにも任せられるようにする（2026-11-27）

- **決定**: 内蔵の取得（cpal）に加えて、`--capture-cmd` を持つ。
- **理由**: 実装した環境（Linux）では、macOS の Core Audio の経路をビルドも実行もできなかった。動かなかった
  場合の逃げ道が要った。同じ仕組みが、Linux 上での通し試験にも使えた。
- **結果**: macOS では、内蔵の取得が最初から動いた。

### 録音の許可は接続元が持ち、既定は disarmed にする（2026-11-27）

- **決定**: 設計メモの方針をそのまま採った。`recording = armed && connected && requested`。
- **再検討（同日）**: 実際には `--armed` で常用することになり、「手で切り替える仕組みは無駄ではないか」という
  疑問が出た。結論は次のとおり。
  - 区別は残す。止めるスイッチとしての価値があり、armed のときのコストが無い。
  - 既定を armed にはしない。公開しているツールなので、何も考えずに入れた人のマイクが開く状態を避ける。
  - 手で切り替える代わりに条件を自動で判定する案（ターミナルが最前面のときだけ、など）は、急がない。
    しばらく使って、気になる場面が出てきたら検討する（[07](../07-roadmap.md)）。
- **整理**: この仕組みが守るのは、「接続先で利用者の権限を得た者」に対してだけである。ネットワーク上の
  第三者と、接続先の別のユーザーは、通信方式の時点で入口が無い（[05](../05-security.md) §1）。

### 音声の接続を、端末の接続と別に張る（2026-11-27）

> ⚠ **一部改定済み**（別に張るのは既定。相乗りを選べるようにした）→「多重化に相乗りして、認証を 1 回にする」（2026-11-27）

- **決定**: micmux の ssh には `ControlMaster=no` と `ControlPath=none` を付け、端末用の接続と TCP を分ける。
  端末の大量の出力に音声が待たされないようにするため。

### `ssh` に連動して自動で起動する（2026-11-27）

- **経緯**: 音声用の接続を別の端末で起動するのが手間だった。
- **選択肢**: (A) `~/.ssh/config` から ssh に連動して起動・終了する、(B) 接続元に常駐させる（launchd）、
  (C) ssh を包むシェル関数。
- **決定**: A。既存の SSH の使い方を変えず、マイクの許可も端末アプリのものをそのまま使える。
  B は、launchd から起動したコマンドにマイクの許可が出るかが不確かだった。
- **仕組み**: `--background`（端末から切り離す）と `--watch-pid`（指定した ssh の終了に追従する）。
  同じホストへの 2 本目以降の ssh は、動いている client に自分を登録するだけにし、登録された ssh が
  すべて終わったら client が終わる。
- **再帰の防止**: micmux 自身の ssh でも起動のきっかけが発動するので、それを止める
  （[02](../02-architecture.md) §5.3）。

### 裏へ回るときは、fork するだけでなく自分を起動し直す（2026-11-27）

- **経緯**: 最初の実装は、fork して親が戻るだけだった。
- **決定**: 自分自身を新しいセッションで起動し直す。macOS では、fork しただけの子プロセスから Core Audio
  などを使うと動作が保証されないため。
- **補足**: 最初に自動起動が動かなかった原因は、これではなかった（接続元が古い版のままだったことと、
  disarmed のままだったこと）。それでも、macOS で問題になりうる弱点なので改めた。

### 多重化に相乗りして、認証を 1 回にする（2026-11-27）

- **経緯**: 接続のたびに指紋認証が要る鍵を使っていて、接続が 2 本だと認証も 2 回になった。
- **決定**: `--mux` を追加し、端末用の ssh が作ったマスターに相乗りできるようにする。既定は変えない。
- **起動のきっかけを `Match exec` に変える**: 相乗りした 2 本目以降の ssh では `LocalCommand` が走らない
  ことを、検証用の sshd で確かめた。`Match exec` は毎回走り、`$PPID` はその ssh を指す。
- **端末側の認証を待つ**: 待たないと、micmux の ssh が先に認証を始めて 2 回になる。
- **`ControlPersist` を必須にする**: 無いと、ログアウト時に端末用の ssh と micmux が互いの終了を待ち合う。
- **根拠（実測）**: 検証用の sshd で、端末 2 本と micmux の計 3 接続に対して認証は 1 回だった。macOS と
  指紋認証の鍵でも動いた。遅延は、接続を分けた場合と差が無かった（[04](../04-audio.md) §6）。
- **引き換え**: 音声と端末が同じ TCP を通る。認証済みの接続を、接続元の同じユーザーのプロセスが借りられる
  時間ができる（[05](../05-security.md) §3.6）。利用者は、再認証が多いぶんには構わないとして、
  `ControlPersist` を 1 分にした。

### 連続録音時間の上限を、無効にできるようにする（2026-11-27）

> ⚠ **一部改定済み**（上限に達したときの動作）→「上限に達したら disarm する」（2026-11-28）

- **経緯**: 既定の 120 秒で録音が止まった。キーを押したまま考える時間があるので、上限が邪魔になった。
- **決定**: `--max-seconds 0` で無効にできるようにする。
- **引き換え**: 止める仕組みが、キーを離すことと `micmux disarm` だけになる。

### 無音のあいだ音声を送らないオプションは入れない（2026-11-27）

- **決定**: 入れない。待機中はもともと何も送っておらず、録音中も 32 KB/秒である。節約できるのは
  キーを押したまま黙っている時間だけで、語頭・語尾が欠けて認識精度が落ちるおそれのほうが大きい。

### 後から来た bridge が、前の bridge を終わらせる（2026-11-27）

- **経緯（コードレビューの指摘）**: 接続元がスリープすると、古い bridge が残る。再接続した新しい bridge は
  既存の仮想マイクを借りて動き、古い bridge が後で終わるときにそれを消してしまう。
- **決定**: 排他用のファイルのロックの持ち主を OS から引き、SIGTERM（終わらなければ SIGKILL）で終わらせる。
  同じ仮想マイクを使う接続は、後から来たほうが優先される。

### bridge は、無通信が 45 秒続いたら終わる（2026-11-27）

> ⚠ **改定済み** →「無通信で終わるまでの時間は 30 分にする」（2026-11-27）

- **決定**: client は 10 秒ごとに Ping を送る。bridge は、45 秒間何も届かなければ後片付けをして終わる。

### 無通信で終わるまでの時間は 30 分にする（2026-11-27）

- **経緯**: 45 秒は、依頼の中で例として挙げた値がそのまま実装されたもので、検討が足りていなかった。
- **問題**: 接続元のふたを数分閉じただけなら、SSH の接続は生きていることが多い。45 秒だと bridge だけが
  先に終わり、端末は使えるのに音声だけ使えなくなる。
- **決定**: 30 分にする。仮想マイクが壊れる問題は「後から来た bridge が前の bridge を終わらせる」で解決して
  いるので、こちらは接続元が戻ってこない場合の掃除でしかなく、長くてよい。
- **根拠（実測）**: 数分のスリープから復帰したあと、SSH を開き直さずに音声入力が使えた（bridge は同じ
  プロセスのままだった）。

### レビューを、コードレビュー → 簡素化 → セキュリティの順に行う（2026-11-27〜28）

- **決定**: 3 つを並行ではなく順番に行う。前の段の修正が、後の段の対象に入るようにするため。
- **結果**:
  - コードレビュー: 11 件。すべて修正した。
  - 簡素化: `client.rs` を `control.rs`・`ssh.rs` に分け、重複をまとめた。挙動は変えていない。
  - セキュリティレビュー: 重大なものは無し。中 2 件と軽微 4 件を修正し、軽微 3 件は issue にした。
- 見送った指摘は [07](../07-roadmap.md) の表にある。

### 新しい Rust の機能を、lint のためだけには使わない（2026-11-27）

> ⚠ **改定済み** →「対応する Rust の最低版を 1.89 にする」（2026-11-28）

- **経緯**: 簡素化の中で、lint の警告を消すために、Rust 1.87・1.88 以降の機能を使う変更が入りかけた。
- **決定**: 古い書き方に戻す。接続元の側のツールチェーンの版がわからず、ビルドが通らなくなるおそれがある。
  最低版をどうするかは未決（[#7](https://github.com/Daiius/micmux/issues/7)）。

### 上限に達したら disarm する（2026-11-28）

- **経緯（セキュリティレビューの指摘）**: 上限に達して録音が止まっても、接続先が START を送り直すだけで、
  利用者の操作なしに再開した。ログの「続けるには `micmux arm`」という表示も、実態と合っていなかった。
- **決定**: 上限に達したら disarm する。録音中に届いた START で、時間を数え直さない。
- **残る性質**: armed のあいだ、上限より短い録音は何度でも始められる。仕組みとして避けられないので、
  既知の制限として明記する（[05](../05-security.md) §2.2）。

### 接続先から届く文字列と量を制限する（2026-11-28）

- **経緯（セキュリティレビューの指摘）**: 想定外のメッセージを丸ごとログに書いていて、約 20 MB の送信で
  ログが約 90 MB になった。接続先の標準エラーも、そのままログに流れていた。
- **決定**: 種類と長さだけを書く。標準エラーは、行の長さ・行数・総量を制限し、制御文字を取り除く。
  ログは本人だけが読める権限にし、大きくなったら退避する。
- **受け渡しの上限のかけ方**: 経路全体に上限をかけると、録音の停止処理と互いに待ち合って固まる。
  接続先から届く分だけを数えて制限する。

### 対応する Rust の最低版を 1.89 にする（2026-11-28）

- **経緯**: 最低版が決まっていないために、lint の警告を 1 件残していた。
- **決定**: `rust-version = "1.89"` にする。同じ作者の bellmux と同じ値で、接続元でそれをビルドできている
  なら足りるはず、という推測から選んだ。最低版が決まったので、残していた警告を解消した。
- **根拠**: CI の `msrv` ジョブが、1.89 でビルドできることを確かめた。

### CI を入れ、macOS のランナーでも回す（2026-11-28）

> ⚠ **一部改定済み**（macOS のランナーをやめた）→「CI は Linux だけで回し、通しの試験を足す」（2026-11-28）

- **経緯**: macOS 向けの分岐は、Linux ではビルドできず、利用者の実機でしか確かめられていなかった。
  レビュー対応でその分岐に手を入れたときも、利用者が更新してビルドするまで、通るかわからなかった。
- **決定**: ビルド・テスト・lint を、Linux と macOS のランナーで回す。依存関係の照合（`cargo audit`）と、
  全履歴の秘密の検査（Betterleaks）も入れる。
- **方針**: workflow の権限は読み取りだけにする。外部の Action は `actions/checkout` だけを使い、
  ほかのツールは公式の配布元から直接入れる。
- **限界**: CI で確かめられるのは、ビルドと、マイクを使わない単体テストまで。実際に音が通るかは
  実機で確かめる。

### CI は Linux だけで回し、通しの試験を足す（2026-11-28）

- **経緯**: macOS のランナーが、データセンターに並べた実機の Mac で動いていると知った。手元に接続元の
  Mac があるのに、その資源を使うのは割に合わない、と利用者が判断した。一方で、接続元を Linux にしたい
  のに、マイクの付いた Linux の実機が手元に無い。
- **決定**:
  - macOS のジョブを外す。macOS 向けの分岐は、利用者の実機で確かめる。
  - 文書だけの変更では、ビルド・テスト・lint を回さない。
  - Linux のランナーで、音声の通しの試験（`scripts/e2e-linux.sh`）を回す。代役のマイクから仮想マイクまで、
    内蔵の取得の経路も含めて通す。
- **引き換え**: macOS 向けの分岐のコンパイルエラーは、マージして利用者が更新するまでわからなくなる。
  macOS のランナーを入れた直接の動機だったが、承知のうえで外した。
- **副産物**: 通しの試験は、bridge の音声サーバーを使う部分の初めての自動試験でもある。それまでの
  単体テストは、そこを一切通っていなかった。

### 仮想マイクを既定の出力先にしないよう、出力の捨て先を用意する（2026-11-28）

- **経緯**: 「エージェント以外の音声の利用と干渉しないか」を洗い出す中で、実運用の接続先の状態を見たところ、
  既定の出力先が仮想マイクになっていた。仮想マイクは null sink（出力デバイス）とその monitor でできている。
  実体のある出力先が無いサーバーでは、音声サーバーの置く代役（`auto_null`）が仮想マイクの sink に置き換わり、
  それが既定に選ばれる。
- **再現（隔離した環境）**: 出力先を指定せずに鳴らした音が、そのままの大きさで仮想マイクに届いた。
- **決定**: 出力の捨て先の null sink を別に作り、そちらを既定の出力先にする。仮想マイクの sink を作る前に行う。
- **採らなかった案**:
  - 仮想マイクを、sink を持たない方式（FIFO から読む source）で作り直す。筋はよいが、バッファの扱いと
    名前（`<名前>.monitor`）が変わり、確かめ直す範囲が広い。
  - sink の優先度を下げる。出力先がそれ 1 つしか無ければ、優先度が低くても既定に選ばれる。
- **試験**: 通しの試験の音声サーバーに代役の sink を置き、実運用と同じ状態にした。既定の出力先が仮想マイクで
  ないことと、出力先を指定せずに鳴らした音が届かないことを確かめる。修正前の bridge では失敗する。
- **レビューでの追加（同日）**: 起動時に 1 回確かめるだけでは足りなかった。
  - 別の名前の仮想マイクを使う bridge が先に終わると、残った仮想マイクが既定に選ばれる。音声サーバーの
    通知を受けるたびに見直して、捨て先に替えるようにした。順序に依存しない方法を選んだ。
  - 既定の出力先を調べるコマンドの失敗を「既定が無い」と同じに扱っていた。確かめられなかったときは
    書き換えないようにした。実体のある出力先を既定から外すほうが、混入より害が大きいと判断した。
  - どちらも、修正を無効にすると通しの試験が失敗することを確かめた。
- **残したもの**: 接続元の入力デバイスとチャンネルを選べない件（[#12](https://github.com/Daiius/micmux/issues/12)）と、
  接続中に既定の録音デバイスが切り替わる件（[#13](https://github.com/Daiius/micmux/issues/13)）は、issue にした。

### 秘密の検査は、push の前と CI の 2 段にする（2026-11-28）

- **決定**: 同じ作者の他のリポジトリのやり方に合わせる。push 前の検査は、リポジトリの hook
  （git の config ベース hooks）。CI は、範囲を計算せず毎回全履歴を検査する。コミット時の検査は、
  ホストのグローバルな hook に任せ、リポジトリ側では持たない。
- **補足**: 秘密の検査は、ホスト名やユーザー名のような環境を特定する情報を拾えない。そちらは、
  コミットや issue を出す前に、書いた側が検索して確かめている。

### PR はレビューボットにかけ、merge commit でマージする（2026-11-28）

- **経緯**: 最初の 9 コミットは、main に直接 push していた。PRD を書いた時点で、レビューボット
  （oculibis）の設定を入れ、以後は PR にすることにした。
- **決定**: PR は、CI が通り、レビューボットの指摘がゼロになってからマージする。マージは merge commit。
  レビュー指摘への対応などの、コミットごとの履歴を残すため。
- **設定を先に入れてから PRD を出す**: レビューボットは、設定を default branch から読む。先に設定を
  main に入れておくと、PRD を出す PR そのものを、実装との食い違いの検査にかけられる。実際に、
  記述の曖昧さを 1 件指摘された。

### 動作試験は、利用者の音声サーバーとは別のインスタンスで行う（2026-11-27）

- **経緯**: 実装中の試験の後片付けで、プロセスを名前で指定して止めたところ、利用者が実際に使っていた
  音声サーバーを止めてしまった。そのとき動いていた接続も切れた。
- **決定**: 試験用の音声サーバーは、環境変数で隔離して別に立て、PID を指定して止める。プロセスを名前で

### PipeWire での通しの試験を CI に足す（2026-11-28）

- **経緯**: 最近のデスクトップ向けのディストリビューションは PipeWire が既定で、PulseAudio でしか
  確かめていないと、ほかの人の手元で動くと言えない。コンテナの中の PipeWire 1.4.2 で試したところ、
  micmux を変えずに、通しの試験・`--set-default`・ALSA で録るアプリからの録音要求が通った。
- **決定**: 通しの試験に `E2E_SERVER=pipewire` を足し、CI の `e2e-pipewire` ジョブで変更のたびに回す。
  ALSA のプラグインが既定デバイスを取り合うので、PulseAudio のジョブとは分ける。
- **試験の側の違い**: PipeWire の ALSA プラグインは `PULSE_SOURCE` を見ない。内蔵の取得の試験では、
  代役のマイクを既定の録音デバイスにもする。
- **試験用の PipeWire の隔離**: WirePlumber は、既定では実際のデバイスを探して掴む。試験用のインスタンスでは
  デバイスの監視を止め、利用者の設定と `PIPEWIRE_REMOTE` などの環境変数も読ませない。レビューでの指摘による。
  設定の書き方が違う WirePlumber 0.4 では、PipeWire での試験を回さない。
- **残したもの**: 実際の音声デバイスがある機械での確認。Debian と Ubuntu 以外のディストリビューション。

### 接続先の仮想マイクの遅れは、音声サーバーによる。PulseAudio 向けの対処は入れない（2026-11-28）

- **経緯**: 通しの試験で、録音要求から最初の音声まで約 2 秒かかっていた（#15）。調べると、PulseAudio の
  null sink の monitor は、録り始めてから最大で約 2 秒、音を出さない。micmux を通さなくても起きる。
  接続先の仮想マイクも null sink なので、実際の音声入力でも、音が 1〜2 秒遅れて届いていた。PipeWire では
  約 0.15 秒である。
- **試したもの**: 仮想マイクに無音を流し続ける（遅れは消えるが、待機中も CPU を使う。遅延 500 ms 指定で
  1 コアの 0.2 %）。bridge が直接書き込む source にする（`module-pipe-source`。PulseAudio では最良だが、
  PipeWire では遅れが増え、前の録音の音が次の録音に出る）。
- **決定**: どちらも入れない。micmux を選ぶ理由の 1 つが、待機中に資源を使わないことなので、待機中の CPU を
  0 に保つことを優先する。遅れが気になる接続先では、音声サーバーを PipeWire に替える。替えるためのスクリプトを
  用意する。
- **利用者の判断**: 待機中にずっと CPU を使う動作にはしたくない。1 % に満たない程度ならよい、という線だった。
  PulseAudio の遅れは、我慢できないほどではない、という感想でもあった。
- **残したもの**: セットアップ用のスクリプトが入れる音声サーバーを、PipeWire に変えるかどうか。

### PipeWire で既定の録音デバイスにするときは、独立した source を作る（2026-11-29）

- **経緯**: 実運用の接続先を PipeWire に切り替えたとき、脆弱性の修正が入っている backports の版（1.6.9）を
  入れたところ、音声入力が動かなくなった。PipeWire 1.6 系では、既定の録音デバイスが sink の monitor のとき、
  デバイスを指定しない録音が、既定の出力先（捨て先）の monitor に繋がる（#18）。安定版（1.4.2）に戻して
  動かした。Debian の開発版（1.6.11）でも同じ動きだったので、一時的な不具合としては扱えない。
- **決定**: PipeWire で `--set-default` を付けたときは、monitor ではない独立した source（`<sink 名>_mic`）を
  作って既定にし、録音セッションのあいだだけ、sink の monitor ポートから `pw-link` でつなぐ。
- **なぜ録音のあいだだけか**: つないだままにすると、sink も source も休止できず、待機中に 1 コアの 約 0.5 % を
  使い続ける。
- **採らなかった案**: 出力と録音の両方の顔を持つデバイス（名前を指定した録音が繋がらない）。monitor を包む
  source（録音ストリームが常に 1 本残り、前の録音の音が次に出る）。
- **代償**: PipeWire のときだけ、`pactl` と `pacat` のほかに `pw-link` を使う。既定にするデバイスの名前が、
  音声サーバーで違う（PulseAudio は `micmux.monitor`、PipeWire は `micmux_mic`）。

### 通しの試験は、アプリと同じ形で録る検査を含める（2026-11-29）

- **経緯**: 上の不具合を、CI は見逃していた。通しの試験が、仮想マイクを名前で指定して録っていたためで、
  既定の録音デバイスから録る Claude Code の経路を通っていなかった。backports の版を勧める前に、コンテナで
  通しの試験を回して「通る」と確かめていたが、同じ理由で意味が無かった。
- **決定**: `--set-default` を付けた bridge に対して、デバイスを指定しない録音（`parec` と、ALSA の既定デバイス
  からの `arecord`）で音が届くことを、通しの試験で確かめる。同時に既定の出力先へ別の音を鳴らし、録れた音の
  高さで、繋がった先を見分ける。修正前の版が、この検査で落ちることを確かめた。
